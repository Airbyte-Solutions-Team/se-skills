- **Tombstone reconciliation never gives up, and the cross-system partial failures are proven (Slice 6B2A1 review follow-up, August 26).** The first version of the cleanup claim skipped a tombstone once `cleanup_attempts` reached `p_max_attempts`, which is the wrong failure mode for this particular job: the row is already hidden and the deletion is already recorded, so an exhausted attempt budget during a Storage outage would have left customer content the customer asked to delete sitting in the `transcripts` bucket forever, with no queue entry, no retry, and no operator surface (Slice 6B2B) to find it. Retries are now unbounded and the backoff is durable instead: `release_transcript_cleanup` persists `cleanup_next_attempt_at = now() + min(2^attempts, cap)` (cap one hour) and the claim only considers due rows, ordered by that timestamp, so a transient outage costs delay rather than the deletion, the schedule survives worker restarts because it lives on the row rather than in worker memory, and `cleanup_attempts`/`cleanup_last_error` stay the signal that a tombstone is struggling. The two cross-system partial failures Postgres and Storage cannot make atomic now have behavioural tests rather than reasoning: a Storage delete that *removes the object and then raises* leaves the row `pending` and hidden with no false completion, and the next attempt sees `ObjectNotFound` and finalizes with no second `transcript_delete` event; and a Storage delete that succeeds while the finalizing `UPDATE` fails (the finalize call is now its own `_finalize_transcript_cleanup` method so a real database failure can be injected there) leaves the row tombstoned, hidden, and lease-held, never recreates the object, and is finalized by a restarted worker after the lease expires. - **Transcript deletion tombstone and durable Storage reconciliation (Slice 6B2A1, August 26).** Deleting a hosted transcript used to delete the private object first and the metadata row second, so a database failure in between left a listable row with no object and no delete evidence, and a Storage failure could report a deletion that had not happened. Deletion is now authorize → tombstone → reconcile. Migration `013` adds `tombstoned_at`, `delete_requested_by`, `cleanup_state`, `cleanup_completed_at`, and lease/attempt/error columns to `public.transcripts` with check constraints that keep a live row (`none`, no completion timestamp) distinguishable from a tombstoned one (`pending`/`complete`). `public.request_transcript_deletion` replaces direct `app_user` deletion: it is `app_admin`-owned `SECURITY DEFINER` with an empty search path, derives the actor from the signed tenant context and the organization from the locked row, treats missing, cross-organization, and wrong-account/opportunity requests identically (`SE020` → `404`), refuses while a `queued` or `running` job references the transcript (`SE021` → `409`) without implicitly cancelling anything, and commits the tombstone plus exactly one `transcript_delete` event in the same transaction — so the event now precedes any Storage call instead of following a successful one, and a concurrent duplicate or replayed request returns `already_deleted` and appends nothing. `DELETE`/`UPDATE` on the table is revoked from `app_user`, the `SELECT`/`INSERT` policies carry `tombstoned_at IS NULL`, and `public.enqueue_job` rejects a tombstoned transcript, so hiding and run-eligibility are database invariants: the content leaves lists, downloads, corrections, and new runs the instant the tombstone commits, even through direct `app_user` SQL, and the delete/enqueue race has one safe winner.
